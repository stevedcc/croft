# Security review: Croft 0.6.2 as deployed (2026-10-19)

Reviewed at commit `0e9e697` (Croft 0.6.2) against the deployment the repository describes:
anonymous readers on the static SSR pages, staff signing in through OIDC to the Blazor Server
admin, the API behind the Web app on a ClusterIP Service, PostgreSQL, the mounted branding and
site-files folders, the `/api/media/{id}` proxy, the page-view beacon, `/csp-report`, WebFinger,
and the `k8s/` base. Findings are ranked by how easily they can be exploited on that deployment.
Severity: Critical / Important / Minor. Evidence is quoted from the code or from running it; where
something could not be run here it says "unverified".

How the claims were checked (details under "Verification record" at the end): the solution was
built, the Web unit suite was run, and three experiments were run outside the repository (the real
`MarkdownRenderer` and `LocalUrl` from the built `Croft.Web`, and a minimal Kestrel app driven by
curl and Chromium). The API integration suite needs a Postgres Testcontainer and no container
runtime exists in this environment, so it is unverified; the E2E suite was not run.

## Findings

### 1. Important: slow readers of the media proxy hold the site's request permits; 128 connections return 503 to every reader

**Where.** `src/Croft.Web/Program.cs:257-261` (the limiter), `src/Croft.Web/Program.cs:454-486` (the proxy), `src/Croft.Web/Program.cs:892-905` (the exemptions), `src/Croft.Api/Program.cs:123-128` and `src/Croft.Api/Controllers/MediaController.cs:91` (the same shape on the API).

**What is wrong.** Both apps shed load with one concurrency limiter shared by every client:

```csharp
// src/Croft.Web/Program.cs:257-261
: RateLimitPartition.GetConcurrencyLimiter("pages", _ => new ConcurrencyLimiterOptions
{
    PermitLimit = builder.Configuration.GetValue("Croft:Web:MaxConcurrentRequests", 64),
    QueueLimit = builder.Configuration.GetValue("Croft:Web:RequestQueueLimit", 64),
```

ASP.NET Core's rate-limiting middleware holds the permit until the downstream pipeline completes,
and for the media proxy that is the whole body transfer to the browser:

```csharp
// src/Croft.Web/Program.cs:485
await response.Content.CopyToAsync(context.Response.Body, ct);
```

`IsRateLimiterExempt` (`Program.cs:892-905`) exempts health, `/_blazor`, `/_framework`,
`/csp-report`, site files and static assets, not `/api/media/`. Kestrel's default minimum response
data rate is 240 bytes/s (5 s grace), so a client that reads at 250 bytes/s keeps one permit for as
long as the file takes at that speed: a 2 MB banner image is about 2.3 hours, a 10 MB upload (the
API's limit, `MediaController.cs:18`) about 11 hours. The proxy copies from the API only as fast as
the browser reads, so the API's own permit (`src/Croft.Api/Program.cs:123-128`, also one partition
with 64 + 64) is held for the same time. No request-body or connection limits are configured
either (no `Kestrel` limits in either `Program.cs`).

**Why it matters.** One machine with 128 slow connections per Web pod (two pods: 256 sockets) makes
`/`, every post, search and the admin answer `503 Too many requests`; the same connections
starve the API, so even requests that get a Web permit fail. The limiter was built to protect the
Raspberry Pis from a reader surge; it also hands any anonymous visitor a cheap, sustained
denial of service.

**Evidence (run).** A minimal Kestrel app with the same middleware and `PermitLimit = 1`,
`QueueLimit = 0`: while `/slow` streamed its body for 12 s, `GET /fast` answered `HTTP 503`;
after the stream ended it answered `HTTP 200` (scratch app, transcript in "Verification record").

**Fix.** Partition the limiter per client address (`RateLimitPartition.GetConcurrencyLimiter(ip, ...)`)
with a small per-client ceiling beside the global one, and give `/api/media/` its own partition so
images cannot exhaust pages. Raise `KestrelServerOptions.Limits.MinResponseDataRate` and set
`MaxConcurrentConnections`. Better still, serve media without the Web proxy (ingress route to the
API, or an object store/CDN) so no Blazor pod streams files at all.

### 2. Important: anonymous visitors open Blazor circuits (the not-found and error pages are interactive); 400 of them lock staff out of the admin or exhaust the pod's memory

**Where.** `src/Croft.Web/Components/Pages/NotFound.razor:1-2`, `src/Croft.Web/Components/Pages/Error.razor:1`, `src/Croft.Web/Components/App.razor:94`, `src/Croft.Web/Options/CircuitSettings.cs:21`, `src/Croft.Web/Services/CircuitAdmissionMiddleware.cs:23-32`.

**What is wrong.** The catch-all page has no `[ExcludeFromInteractiveRouting]`:

```razor
@* NotFound.razor:1-2 *@
@page "/not-found"
@page "/{**path:nonfile}"
```

so `App.razor:94` renders it with `InteractiveServer` (`tests/Croft.Web.Tests/CspSnapshots.txt:284-285`
shows the not-found page carrying the interactive policy, and `CookieTests.NotFoundPage_AnInteractiveDocument_...`
names it one). Any `GET /anything` by an anonymous browser therefore prerenders, loads
`blazor.web.js` and opens a circuit. Circuit admission counts circuits, not users:

```csharp
// CircuitAdmissionMiddleware.cs:23-26
if (WouldStartCircuit(context)
    && settings.MaxActive > 0
    && counter.Count >= settings.MaxActive)
```

with `DefaultMaxActive = 400` (`CircuitSettings.cs:21`). README says "Circuits are for admin and the
editor only (a circuit's memory is a real cost; readers must not hold one)"; the 404 page breaks that.

**Why it matters.** An attacker keeps 400 not-found tabs (or 400 raw SignalR connections replaying
the descriptors from one 404 response) open per pod. Every later circuit start, including a staff
member opening `/admin`, is refused with `503 Circuit limit reached`: the editor renders but nothing
works. Without the ceiling the cost is memory: `docs/workarounds.md:446` measures roughly 0.9 MiB per
circuit, so 400 circuits are about 360 MiB of a 512 MiB limit (`k8s/web-deployment.yaml:153`), and
reload churn (W-052) is exactly what OOM-killed the pods before.

**Fix.** Mark `NotFound` and `Error` with `[ExcludeFromInteractiveRouting]` (their content is plain
markup; `NavigationManager.NotFound()` works during static SSR). In `CircuitAdmissionMiddleware`
refuse circuit starts from unauthenticated requests outright, or reserve a share of `MaxActive` for
authenticated staff so anonymous circuits can never consume the whole budget.

### 3. Important: the page-view beacon stores an unbounded, attacker-chosen `referrer` per row; an anonymous client can fill the database

**Where.** `src/Croft.Web/Program.cs:488-512`, `src/Croft.Api/Controllers/AnalyticsController.cs:15-20`, `src/Croft.Api/Models/PageView.cs:12`, `src/Croft.Api/Data/Configurations/PageViewConfiguration.cs:10-16`, `src/Croft.Api/Services/AnalyticsService.cs:85`.

**What is wrong.** The Web endpoint parses whatever body arrives, up to Kestrel's default 30 MB:

```csharp
// src/Croft.Web/Program.cs:509
beacon = await JsonSerializer.DeserializeAsync<PageViewRequest>(context.Request.Body, JsonSerializerOptions.Web, ct);
```

and forwards it with the ingest key. The API stores it anonymously (`AnalyticsController.cs:15-20`)
into `string? Referrer` (`PageView.cs:12`); `PageViewConfiguration.cs` caps only `IpHash`
(`HasMaxLength(128)`), so `Referrer` and `UserAgent` are unlimited `text`. The dedupe is one row per
post, IP hash and day (`AnalyticsService.cs:85`, `ON CONFLICT ... DO NOTHING`), and rows live 90
days (`PageViewRetentionHostedService.cs:25`).

**Why it matters.** One request per published post per day stores up to 30 MB of referrer. From a
single IPv4 address that is `posts × 30 MB` a day; from an ordinary IPv6 /64 the attacker rotates
source addresses and the row count is unlimited. A Raspberry Pi's disk, the WAL, backups and the
read replica all fill, and the API's own `/api/analytics` summary queries slow down. The same body
is also buffered in the Web pod's memory while it is deserialised and re-serialised, so a burst of
large beacons is a memory spike there too.

**Fix.** Bound the beacon: `IHttpMaxRequestBodySizeFeature.MaxRequestBodySize = 4096` on
`/api/analytics/pageview`, reject a `referrer` over 2 KB and a `User-Agent` over 512 bytes in
`AnalyticsService`, add `HasMaxLength` for both columns (a new migration), and rate-limit the beacon
per client address.

### 4. Important: `returnUrl` open redirect after sign-in (a tab or newline defeats `LocalUrl.IsLocal`)

**Where.** `src/Croft.Web/LocalUrl.cs:19-22`, `src/Croft.Web/Program.cs:828-833`.

**What is wrong.** The check rejects `//` and `/\` only:

```csharp
// LocalUrl.cs:19-22
if (url.StartsWith("//", StringComparison.Ordinal) || url.StartsWith("/\\", StringComparison.Ordinal))
    return false;

return true;
```

`/login` stores the value as the OIDC `RedirectUri` (`Program.cs:828-833`), and after the IdP
callback ASP.NET Core's `RemoteAuthenticationHandler` redirects to it verbatim. Browsers strip ASCII
tab and newline anywhere in a URL before parsing (WHATWG URL), so `/<TAB>/evil.example` is
`//evil.example`, a protocol-relative URL to another host. ASP.NET Core's own `IsLocalUrl` rejects
control characters for exactly this reason; `LocalUrl` does not.

**Why it matters.** A link `https://blog/login?returnUrl=/%09/evil.example/admin` looks like a
blog sign-in link. The staff member signs in at the real IdP, the blog sets its real session cookie,
and the browser then lands on `evil.example`, which shows a copy of the admin and a "session
expired, sign in again" form. It is the classic post-login phish, aimed at the two accounts that
can publish on the site.

**Evidence (run).**
- Through the built `Croft.Web` assembly: `LocalUrl.IsLocal("/\t/evil.example") = True` and
  `LocalUrl.IsLocal("/\n/evil.example") = True`.
- A minimal Kestrel app calling `Response.Redirect("/\t/127.0.0.1:5992/landed")` sent
  `Location: /^I/127.0.0.1:5992/landed` (`^I` is the tab; Kestrel accepts HTAB in a header value).
- Chromium (Playwright 1.56, the pre-installed browser) opened on `http://127.0.0.1:5991/r` ended on
  `final URL: http://127.0.0.1:5992/landed`, a different origin.
- The IdP round trip itself was not re-run here (no OIDC provider in this environment); the hop
  that is framework code is `RemoteAuthenticationHandler.HandleRequestAsync`, which calls
  `Response.Redirect(ticketContext.ReturnUri)` without a local-URL check.

**Fix.** Reject any control character (`char.IsControl`) in `LocalUrl.IsLocal`, mirroring
`UrlHelperBase.CheckIsLocalUrl`, and add `"/\t/evil.example"`, `"/\n//evil.example"` and
`"/\r/evil.example"` to `LocalUrlTests.IsLocal_ExternalOrMaliciousUrls_ReturnsFalse`.

### 5. Important: Markdown renders arbitrary attributes and `javascript:` links; the CSP is the only barrier, and staff pages allow inline style

**Where.** `src/Croft.Web/Services/MarkdownRenderer.cs:16-17`, `src/Croft.Web/Components/Blog/PostBody.razor:10`, `src/Croft.Web/Security/Csp/AdminAreaCspContributor.cs:20`, `src/Croft.Web/Components/Pages/Editor/DraftReviewPage.razor:1,37`.

**What is wrong.** The pipeline is

```csharp
// MarkdownRenderer.cs:16-17
.UseAdvancedExtensions()
.DisableHtml()
```

`DisableHtml` only escapes raw HTML. `UseAdvancedExtensions` includes Markdig's GenericAttributes
extension, which writes any `{key=value}` the author types straight into the tag, and link
destinations are not filtered by scheme. The output goes into the page unencoded
(`PostBody.razor:10`, `@((MarkupString)Markdown.Html)`). Run through the real renderer:

```text
IN : ![pic](/api/media/0f8f...){onerror=alert(1)}
OUT: <p><img src="/api/media/0f8f..." onerror="alert(1)" alt="pic" /></p>
IN : [click me](javascript:alert(document.cookie))
OUT: <p><a href="javascript:alert(document.cookie)">click me</a></p>
IN : Normal paragraph{style="position:fixed;inset:0;background:#fff;z-index:9999"}
OUT: <p style="position:fixed;inset:0;background:#fff;z-index:9999">Normal paragraph</p>
```

On the public pages the enforced CSP blocks the handler and the `javascript:` navigation and
`style-src-attr 'none'` blocks the style. On `/admin` and `/editor` the policy adds
`style-src-attr 'unsafe-inline'` (`AdminAreaCspContributor.cs:20`), and the draft-review page
renders another author's draft there (`DraftReviewPage.razor:1` is `/editor/posts/{slug}`, line 37
`<PostBody Markdown="@_rendered" />`). Editors can write their own drafts
(`PostService.cs:396`, `if (!isAdmin && post.AuthorId != userId)`).

**Why it matters.** Today: an Editor puts a fixed, full-viewport `style` on a paragraph of a draft;
the Admin who opens it for review sees an overlay the attacker designed instead of the page, with
the real Publish and feedback controls underneath wherever the attacker leaves a hole, which is
clickjacking inside the admin from an account that is not supposed to be able to publish. Tomorrow:
the README invites sites to add CSP sources with `Csp:Add`; a site that adds `'unsafe-inline'` to
`script-src` (or any future relaxation) turns every one of these into stored XSS by any Editor
against every reader and every Admin, because nothing but the header stands in the way.

**Fix.** Build the pipeline from the explicit extension list without `UseGenericAttributes()`, or
keep it and strip every attribute that is not in an allow-list and every URL whose scheme is not
`http`, `https`, `mailto` or relative (Markdig's `LinkInlineRenderer.Rewriter`, or an HTML sanitiser
over the output). Pin it with `MarkdownRendererTests` cases for `{onerror=...}`, `{style=...}` and
`javascript:`.

### 6. Minor: sign-out is a chain of GETs with no CSRF defence and ends the IdP session too

**Where.** `src/Croft.Web/Program.cs:840-844`, `src/Croft.Web/Authentication/TokenSessionEvents.cs:115-132`.

`GET /logout` redirects to the interstitial, whose script loads `/logout/complete`, which removes
the store entry, signs the cookie out and sends the browser to the IdP's end-session endpoint with
`id_token_hint` (`TokenSessionEvents.cs:128`). The auth cookie is `SameSite=Lax`, so any cross-site
top-level navigation to `/logout/complete` (a link, `window.open`) carries it. A page a staff member
visits can end their blog session and their Authentik session at will, mid-edit (the local draft
backup limits the loss). Fix: make `/logout/complete` a POST with the antiforgery token (the
interstitial becomes a form the script submits).

### 7. Minor: the pods keep the default capability set, a writable root filesystem, privilege escalation and an unused service-account token

**Where.** `k8s/api-deployment.yaml:54-58`, `k8s/web-deployment.yaml:57-62`, `k8s/components/network-policies/kustomization.yaml:2-5`.

The pod `securityContext` sets only `runAsNonRoot: true` and `fsGroup: 1654`; there is no
`allowPrivilegeEscalation: false`, `capabilities: { drop: [ALL] }`, `readOnlyRootFilesystem: true`,
`seccompProfile: { type: RuntimeDefault }` or `automountServiceAccountToken: false` anywhere under
`k8s/` (grep). The network policies are an optional component and define no egress. A code
execution bug in either app (finding 5 under a relaxed CSP, or a future dependency flaw) would start
with Linux capabilities, a writable image, a Kubernetes API token and unrestricted egress. Fix: add
the five settings to both containers (the images already run as uid 1654, so the only change needed
is `emptyDir` mounts for `/tmp`), and move the network-policy component into the base with an egress
rule to the database, the API and the IdP only.

### 8. Minor: forwarded headers trust every proxy in both pods, and the trust rests on an optional network policy

**Where.** `k8s/web-deployment.yaml:114-115`, `k8s/api-deployment.yaml:162-163`, `src/Croft.Web/Program.cs:447`, `src/Croft.Web/Security/Csp/CspReportEndpoint.cs:38`, `src/Croft.Api/Controllers/AnalyticsController.cs:24-34`.

`ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` clears `KnownProxies`/`KnownNetworks`, so any peer that
reaches a pod chooses the client address. The deployment comment says only the ingress can reach
the pods, but that is true only when the optional `components/network-policies` is applied. What
depends on the address: the per-visitor page-view identity (`Program.cs` `visitorIp`), the
`/csp-report` rate-limit key (`CspReportEndpoint.cs:38`) and the API's fallback visitor address
(`AnalyticsController.cs:33`). Any workload in the cluster, or anything reaching a Service, can
forge visitors or exhaust the report limiter for a chosen address. The API needs no forwarded
headers at all. Fix: drop the variable from the API; on the Web set `ForwardedHeadersOptions.KnownNetworks`
to the ingress controller's range (or keep the env var and make the network policy part of the base).

### 9. Minor: access, refresh and ID tokens are stored in clear text

**Where.** `src/Croft.Web/Services/PostgresTokenStore.cs:92-101`, `src/Croft.Web/Data/UserSession.cs:13-15`.

The upsert writes `AccessToken`, `RefreshToken` and `IdToken` as plain columns; nothing protects
them (no `IDataProtector` use in the store). A read of the Web database (a backup, a replica, a
`pg_dump` left around, a SQL-level compromise) yields live refresh tokens for every signed-in staff
member, usable at the IdP's token endpoint together with the client secret from the pod. Fix:
protect the three columns with Data Protection (`IDataProtectionProvider.CreateProtector("tokens")`),
ideally with a key ring that does not live in the same database.

### 10. Minor: `Auth:SessionLifetime` is not enforced in the single-instance deployment, and the in-memory store never purges

**Where.** `src/Croft.Web/Services/InMemoryTokenStore.cs:52`, `src/Croft.Web/Authentication/TokenSessionEvents.cs:77`, `src/Croft.Web/Services/UserAccessTokenService.cs:90-91`, `src/Croft.Web/Program.cs:179-189`.

Only the Postgres purge (`SessionPurgeHostedService`, registered at `Program.cs:183` when `WebDb` is
set) ever looks at `SessionExpiresAt`. The cookie handler checks that an entry exists
(`TokenSessionEvents.cs:77`), the token service checks the access-token expiry only
(`UserAccessTokenService.cs:90-91`), and the in-memory store returns any entry (`InMemoryTokenStore.cs:52`).
Without the Web database a stolen cookie stays valid for as long as the IdP keeps honouring the
refresh token, whatever `Auth:SessionLifetime` says, and entries accumulate until restart. Fix:
treat an entry past `SessionExpiresAt` as missing in `GetAsync`/`OnValidatePrincipal`, and purge the
in-memory store on the same schedule.

### 11. Minor: the CSP report limiter is keyed per address; IPv6 rotation bypasses it and grows the bucket table

**Where.** `src/Croft.Web/Security/Csp/CspReportRateLimiter.cs:26-33`, `src/Croft.Web/Program.cs:896`.

One `Queue<DateTimeOffset>` per client key, pruned once a minute; `/csp-report` is exempt from the
global limiter. A client with a /64 posts 60 reports of 16 KB per address per minute from as many
addresses as it likes: unbounded warning-log volume (25 lines per report) and a bucket table that
grows for a minute at a time. Fix: key IPv6 clients on their /64, cap the number of buckets, and
add a global per-minute ceiling.

### 12. Minor: a missing `sub` claim collapses every user to the literal `"unknown"`, which the ownership checks then share

**Where.** `src/Croft.Api/Identity/UserExtensions.cs:7-15`, `src/Croft.Api/Services/PostService.cs:396`, `src/Croft.Api/Services/FeedbackService.cs:49`.

`GetUserId()` falls back to `"unknown"`. With an IdP whose access tokens carry no `sub`, every
Editor is the same author: each can edit every other Editor's draft and delete every other
Editor's feedback. Fix: reject the request (`401`) when `sub` is absent instead of substituting a
constant.

## Checked and found sound

- **Web and API authorisation.** Every mutating API action carries `[Authorize(Roles = ...)]`; the
  anonymous reads apply `publicOnly` from the caller's role (`PostsController.cs:21-42`,
  `PagesController.cs:51-53`); post-specific media of unpublished posts is refused to non-staff
  (`MediaController.cs:70-77`); Editors update only their own drafts (`PostService.cs:396-399`);
  feedback deletion is author- or Admin-scoped (`FeedbackService.cs:49`). Every admin and editor
  page carries `[Authorize(Roles = ...)]`.
- **Tokens and sessions.** No token in the cookie (`SaveTokens = false`, `Program.cs:136`); a
  128-bit random `blog_sid`; the cookie is rejected when the store entry is gone
  (`TokenSessionEvents.cs:73-87`); refresh is serialised per session with `SELECT ... FOR UPDATE`
  (`PostgresTokenStore.cs:55-81`); every cookie is `Secure` outside Development (`Program.cs:84`,
  `CookieTests`), the auth cookie `HttpOnly` and `SameSite=Lax` by default.
- **Back-channel logout.** Signature, issuer, audience, the `events` object, `jti`, absent `nonce`
  and a five-minute `iat` window are all checked (`BackchannelLogoutTokenValidator.cs:40-121`);
  the endpoint never logs the token and answers 400 on any failure.
- **SQL.** Every raw statement is parameterised (`FromSqlInterpolated`, `ExecuteSqlInterpolatedAsync`,
  `FormattableStringFactory` with identifiers quoted from the EF model, `AnalyticsService.cs:62-92`);
  LIKE wildcards are escaped (`LikeSearch.cs:11`); full-text search goes through `PlainToTsQuery`.
- **HTML, JSON-LD, XML.** Razor encodes every value except the four deliberate `MarkupString`s;
  JSON-LD is serialised with System.Text.Json's default encoder (`SeoHead.razor:201`), which escapes
  `<`, `>` and `&`; the feed and sitemap are built with `XDocument` (`FeedService.cs:50`).
- **Paths.** Media is stored under a generated GUID name and read back through a base-path check
  (`LocalFileStorage.cs:11, 39`); branding files are an exact allow-list (`BrandingService.cs:53-62`);
  site files are validated by name, extension, reserved path and size at startup
  (`SiteFilesService.cs:164-241`); content import checks each media path against its root
  (`ContentImporter.cs:116-120`) and is a CLI command.
- **Uploads.** Extension allow-list plus magic bytes (`MediaService.cs:15-18, 52, 193-214`); no SVG;
  served as `image/*` with `nosniff`, under a `script-src 'none'` policy on the Web host.
- **SSRF and redirects.** The Web app's only outbound calls are the configured API base and the
  OIDC authority; no user value reaches an outbound URL. The in-circuit login redirect
  (`BlogApiClient.cs:74-86`) only ever uses the current page path.
- **CSP.** `CspSnapshots.txt` matches the composed policy; no page is looser than README states;
  scripts are path- and SRI-pinned with no `'unsafe-inline'`, nonces or `'self'`; non-document
  responses carry `script-src 'none'`; Blazor's own `frame-ancestors` writer is disabled.
- **CSRF.** Interactive documents rely on the `SameSite=Lax` auth cookie (a cross-site page cannot
  open the SignalR circuit with it) and antiforgery on forms (`CookieTests.AFormPostToAnAdminPage_...`);
  the static documents post nothing; the beacon and report endpoints are write-only receivers with
  no privileged effect; `/backchannel-logout` validates a signed token.
- **Secrets.** None in the repository (`.env` is ignored; `k8s/secrets.example.md` uses Secrets);
  both apps refuse to start without their keys outside Development; audience validation and HTTPS
  metadata are relaxed only in Development (`src/Croft.Api/Program.cs:44, 55`).
- **Headers.** HSTS, `nosniff`, `Referrer-Policy`, `Permissions-Policy` and COOP on every response
  of both apps, written first in the pipeline; the Kestrel `Server` header is off.
- **Containers.** Numeric non-root user in both images; branding and site files mounted read-only;
  migrations serialised under an advisory lock; no Docker socket, host path or privileged setting.
- **Analytics.** Only published posts count (`AnalyticsService.cs:25-29`); the visitor address is
  HMAC-hashed with a daily salt; staff views are not counted; telemetry export strips addresses,
  tokens and query strings (`TelemetryPrivacy.cs`).
