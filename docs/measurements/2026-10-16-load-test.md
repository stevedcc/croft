# Load test, 2026-10-16 ("cells2")

The earlier run behind the README's "about 160 requests a second" (Croft 0.6.0); superseded by [the 2026-10-23 runs](2026-10-23-load-test.md). Public reads only.

## Setup

| | |
|---|---|
| Version | Croft 0.6.0 |
| Hardware | four Raspberry Pi 4 (the site's own cluster) |
| Layout | "cells": public reads answered from the read cache and the database's read replicas; see [`k8s/README.md`](../../k8s/README.md) ("Database connections") and [brief 09d](../briefs/09d-public-reads-scale-out.md) |
| Tool | k6, open model (a fixed arrival rate, not a fixed number of users), stepped ramp, 2-minute steps |
| Traffic | anonymous GETs of the public pages, the public page mix |

An open model matters: when the site slows down the generator keeps arriving at the same rate, so
a saturated site shows rising latency and then errors, instead of the load backing off.

## Result (Croft 0.6.0)

| Arrival rate (req/s) | Result |
|---|---|
| 40 | p95 37 ms |
| 80 | p95 46 to 49 ms |
| 110 to 120 | p95 68 to 87 ms |
| **160** | **p50 32 ms, p95 270 ms, 0 errors** |
| 169 | p95 677 ms |
| 200 | load shedding (503) starts |
| 231 | the site breaks |

The README's "about 160 requests a second" is the 160 step: the highest step with a p95 under
300 ms and no errors. By 169 requests a second the p95 has more than doubled, from 200 the site
sheds load on purpose (a fast `503`, see the `Croft__Web__MaxConcurrentRequests` settings in the
README), and at 231 it breaks.

## Re-run on 0.6.1 (2026-10-18)

After a placement fix, 160 requests a second gave **p95 758 ms**. The red node was hotter in that
run, so it is not a like-for-like comparison with the 270 ms above. Read "about 160 requests a
second" as the order of magnitude a four-Pi cluster reaches in a good run, not as a guarantee, and
measure your own cluster.
