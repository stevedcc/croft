# Load test, 2026-10-26: Croft 0.7.3 on .NET 11

The first runs on .NET 11, against [the 2026-10-23 runs](2026-10-23-load-test.md) on .NET 10
(Croft 0.6.7). Public reads only, same scripts ([`loadtest/`](../../loadtest/README.md)), same
pages and page weights, same cluster. Two rounds on the same day: the first found a placement
problem in the cluster, the second measured the site after it was fixed.

## Setup

| | |
|---|---|
| Version | Croft 0.7.3: .NET 11 (built against the RC 2 packages, running on the RC 3 runtime image: the `11.0` base-image digest moved the morning of the test), brief 16c's idiom sweep, and four dependency releases since 0.6.7. Read path otherwise as 0.6.7 |
| Hardware | four Raspberry Pi 4 (the site's own cluster): three run one Web, one API and one database instance each, the fourth (3.7 GB) runs neither |
| Path | the site's real ingress: a load balancer in front of the cluster, then Traefik (three pods), TLS 1.3 with ChaCha20-Poly1305 (the Pi 4 has no AES instructions) |
| Tool | k6 from the workstation (the 2026-10-23 runs came from a smaller three-core load generator), open model, stepped ramp: 2-minute steps for the page ramps (200, 400, 600, 700, 800, 900 req/s; compressed to 1100), 90 s for the visitor mix (10, 20, 30, 35, 40 visits/s) |
| Pods | 0.7.3 rolled out 07:30 UTC; round 1 started at 07:42 after the readiness warm-up and ten idle minutes (Croft pods at 10 to 100 millicores) |

## Result

"Clean" means 0 errors and a p95 under 200 ms; "breaks" is the first step with a p95 over about a second or a rising error rate.

| Run | .NET 10, 2026-10-23 | .NET 11, round 1 (Traefik on red) | .NET 11, round 2 (Traefik moved to grey) |
|---|---|---|---|
| Page requests, no compression | clean to **600 req/s** (p95 ~120 ms); breaks ~780 | clean to 400 (p95 ~80 ms); 600 at p95 200 to 330 ms; breaks ~700 | clean to **600 req/s** (p95 130 to 160 ms); 700 at p95 200 to 400 ms; breaks ~800 (p95 0.7 to 1.2 s); 880 sustained at p95 1.3 to 1.7 s, 2 to 4 % errors |
| Page requests, `Accept-Encoding: br, gzip` | clean to **800 req/s** (p95 80 to 185 ms); breaks ~1000 (p95 0.7 to 1 s) | clean to 600 (p95 50 to 115 ms); 800 at p95 330 to 670 ms; breaks ~1000 | clean to **650 req/s**; 800 at p95 200 to 240 ms, 0 errors; 900 at p95 415 to 540 ms; breaks ~1000 (p95 0.83 to 0.91 s, 0.4 to 1.1 % errors); 1100 held a minute at p95 1.0 to 1.1 s before the abort |

## Reading it

- **No regression from .NET 11, and a cheaper request.** Under load the Web pods used 0.35 to
  0.40 core each where the .NET 10 run saw 0.45 to 0.6 at the same rates; the API stayed at
  about 15 millicores (the output cache answers) and the database under 0.1 core. Below
  400 req/s, where nothing queues, the p95 is a few milliseconds lower than on .NET 10.
- **The middle of the ramp is TLS, not Croft.** From about 500 req/s the p95 is set by the
  first node to saturate, and that node spends its CPU encrypting responses in Traefik. A faster
  runtime does not change that; the layout does (next point). The compressed ramp sits about
  200 req/s further out on both days because Brotli cuts the bytes through TLS to a third
  (4.9 MB/s against 14.7 MB/s at 600 req/s).
- **Round 1 measured a stale layout.** Traefik's edge-node label still described the cluster of
  2026-10-21; after the node reboots of 2026-10-23/24 both database primaries had failed over to
  the same node as a Traefik pod and a full Croft cell. That node ran at 97 % CPU while the node
  without Traefik idled at 35 %, and the Traefik pods were loaded 0.6 / 0.9 / 0.97 core. Moving the
  label (and the pod) to the idle node gave round 2: Traefik at 0.48 / 0.55 / 0.59 core, the knee
  back where the .NET 10 run had it, and the top end higher. The cluster repo's Traefik config
  records the rule and the gotcha (a `rollout restart` can put a pod straight back, because a
  terminating pod still counts for the hard anti-affinity; delete the one misplaced pod instead).
- **The top-end gain is partly the client.** The 2026-10-23 figures above 800 req/s were limited
  by the three-core load generator as much as by the site (its README says so); today's runs came
  from the workstation. Treat the halved medians at 800+ as "at least as good", not as a measured
  .NET 11 gain.
- **The visitor mix is the same byte ceiling in another costume:** assets are already compressed
  or incompressible, so 30 to 35 visits/s is about 10 to 12 MB/s through TLS, as before. Its clean
  limit moved from 30 to 20 visits/s against 2026-10-23, inside the spread between the two rounds
  today (30 visits/s went from p95 180 to 880 ms to 80 to 530 ms with the layout change alone).

## What this does not show

- Anonymous reads only: no signed-in traffic, editor or uploads.
- .NET 11 is not isolated: 0.7.3 also carries brief 16c and four smaller releases. The per-request
  CPU and the low-load latency are the runtime's to claim; the rest is the whole release.
- Raw k6 output is kept outside this repository (the owner's observability repo).
